# Data Visualisation — the direction, and what it costs

방향 문서. 이 문서는 계약이 아니라 **계획**이고, 그 점에서 `docs/` 의 다른
문서들과 다르다. 나머지는 이미 지은 것을 서술하고, 이 문서는 아직 짓지 않은
것을 서술한다. 그래서 여기 적힌 것은 전부 **아직 증거가 없다.**

근거가 되는 발행 글: [`think/not-someone-who-draws-charts`](https://goldibug.com/ko/think/not-someone-who-draws-charts).

---

## 출발점 — 센 결과

리포트가 권장하는 스택을 이 아카이브에 대고 한 칸씩 셌다. 숫자는 사이트에서
열어 볼 수 있는 글의 개수다.

| 칸 | 증거 |
|---|---|
| TypeScript · React | 3편 |
| SVG | **9편** — 손으로 쓴 인라인 도식 |
| **D3** | **0편** |
| 데이터 변환 · SQL | 2편 |
| 시각화 이론 | **셀 수 없음** |
| 접근성 · 성능 | 3편, **공백 1** |

두 칸이 특별하다.

**`시각화 이론` 을 0 이라고 적지 않았다.** 도식 9개를 그리며 매번 무엇을
어떻게 보여줄지 골랐지만 이론으로 고른 게 아니라 글의 논지에서 역산했다.
증거가 0 인 것과 판정 기준이 없는 것은 다르다. 전자는 만들면 되고 후자는
먼저 배워야 한다.

**`접근성` 의 공백 1 이 가장 아프다.** `docs/PRODUCTION.md` 가 스스로 적어
뒀다 — "Keyboard access to the WebGL field ... is not done". 가장 많이 쓴
주제에서 가진 유일한 시각화가 떨어진다. D3 0편은 안 해서 없는 것이고, 이건
해 놓고 빠뜨린 것이라 성질이 다르다.

## 전략 문서가 말하지 않는 것

출처 리포트에 **어떤 공공데이터를 쓰라는 내용은 없다.** 전체에서 공공데이터는
한 번 나오고, 2개월차 결과물의 "뉴스/공공데이터 3개를 다시 설계"가 전부다.
데이터셋 이름도, 출처도, 고르는 기준도 없다.

있는 것은 프로젝트의 **모양**과 기록 구조다.

| | 리포트가 요구하는 것 |
|---|---|
| 프로젝트 1 | 복잡한 데이터를 명확하게 설명하는 analytical dashboard |
| 프로젝트 2 | 지도 / 시계열 / 네트워크 중 하나를 활용한 interactive visualization |
| 프로젝트 3 | React + D3 기반 재사용 chart system |
| 기록 | 문제 정의 → 데이터 → **시각화 선택 이유** → interaction → 성능/접근성 → 결과 |

마지막 줄이 실질적으로 가장 무겁다. "시각화 선택 이유를 기록하라"는 요구가
정확히 위에서 "셀 수 없음"으로 남긴 칸이다.

---

## 차별점은 데이터셋이 아니라 게이트다

D3 대시보드는 흔하다. 이 아카이브가 증명하는 것은 다른 것이다 — 실측으로
결정을 뒤집은 기록(`make/work-calendar`: 배포 18건 대 업무 11건), 빌드를
실패시키는 대비 계약, 예산 게이트, 결정을 글로 남기기.

> **아무의 D3 대시보드도 대비 비율 때문에 자기 빌드를 실패시키지 않는다.**

그것이 이 포트폴리오의 차별점이어야 한다. 데이터셋이 아니라.

### 따라갈 패턴

| 범주 | 출처 | 패턴 |
|---|---|---|
| 게이트 | `scripts/check-contrast.mjs` | 스타일시트를 파싱해 실측하고 계약과 어긋나면 실패 |
| 계약 데이터 | `lib/tokens.data.ts` `CONTRAST_CONTRACT` | 값이 아니라 **약속**을 기록. 단일 출처는 CSS |
| 죽은 참조 | `scripts/check-practice.mjs` | permissive 하게 수집하고 형식은 별도 규칙으로 |
| 음성 테스트 | 이 저장소의 게이트 전부 | 통과만 하는 게이트는 쓸모없다 |

## 데이터셋 — 이름보다 거르는 기준

### 라이선스: 공공누리 3·4유형은 쓸 수 없다

공공데이터포털의 데이터는 **공공누리(KOGL)** 네 유형으로 이용 범위가 갈린다.

| 유형 | 상업적 이용 | 변경 |
|---|---|---|
| 제1유형 | 가능 | **가능** |
| 제2유형 | 금지 | 가능 |
| 제3유형 | 가능 | **금지** |
| 제4유형 | 금지 | **금지** |

**시각화는 2차적 저작물(변형)이다.** 3·4유형으로 차트를 만들면 이용조건
위반이고, 위반 즉시 이용허락이 종료된다. 포트폴리오는 상업적으로 읽힐 수
있으므로 **제1유형만** 안전하다.

유형은 데이터셋마다 다르고 상세페이지의 공공누리 마크로 표시된다. **개별
데이터셋의 유형은 확인하지 않았다** — 고를 때 그 마크를 먼저 봐야 한다.
출처 표시는 모든 유형에서 필수이고, 온라인이면 원본 링크까지 걸어야 한다.

### 이 사이트에만 걸리는 기준

**한/영 이중언어다.** 라벨이 한국어뿐인 데이터셋을 쓰면 시각화마다 번역
문제가 따라온다. 축·범례·툴팁이 두 언어로 성립하는지를 **데이터를 고를 때**
봐야 한다. 나중에 붙이면 레이아웃이 두 번 깨진다. 이 저장소는 그 비용을
이미 안다 — `check:release` 가 영어 description 이 160자를 넘는 것을 잡은
적이 여러 번 있다.

### 나머지 기준

- 인터랙션이 필요한 크기일 것. 20행짜리는 표로 충분하다
- 갱신될 것. 신선도와 스트리밍을 보일 수 있다
- **질문이 있을 것.** "이 데이터를 보세요"가 아니라

### 후보 출처

| 출처 | 성격 | 확인 필요 |
|---|---|---|
| KOSIS 국가통계포털 | 100대 지표(인구·고용·물가·가계), JSON/XML, 인증키 | 지표별 공공누리 유형 |
| 공공데이터포털 `data.go.kr` | 가장 넓음, 기관별 오픈API | 데이터셋별 유형 |
| 서울 열린데이터광장 | 서울 한정, 생활인구·교통 | 데이터셋별 유형 |

## 프로젝트 셋

### 1 — 교정 대시보드

리포트 3개월차 결과물이 "통계적으로 잘못 해석하기 쉬운 차트 10개 교정"이다.
그것을 숙제가 아니라 **제품**으로 만든다.

널리 인용되는 한국 공공통계 차트 N개를 **원본 인코딩과 교정본을 나란히**
놓고, 왜 원본이 틀린 결론을 부르는지 적는다. `think/statistics-notation` 과
`think/why-contrast-came-first` 의 직접 후속이고, "시각화 선택 이유를
기록하라"는 요구를 제품 구조 자체로 만족한다.

### 2 — 접근 경로를 먼저 설계한 지도

지도는 키보드와 스크린리더로 만들기 가장 어려운 시각화다. 그래서 차별점이
가장 크게 드러난다 — 접근 경로를 **먼저 설계하고** 그 과정을 기록한다.
Phase 0 에서 갚은 키보드 부채가 여기서 재사용된다.

### 3 — 게이트가 붙은 chart system

`CONTRAST_CONTRACT` 와 `check:contrast` 를 차트로 확장한다. 시리즈 색이
**양쪽 바탕 모두에서** 대비를 통과하는지, 색각 이상에서 구별되는지, 예산을
넘지 않는지를 빌드가 검사한다.

## 페이즈

| | 내용 | 산출 |
|---|---|---|
| **0** | **키보드 부채 상환** — WebGL 필드에 roving tabindex | `PRODUCTION.md` 의 "Open, deliberately" 한 줄이 지워짐. TRACE 1편 |
| 1 | 시각화 이론 — "셀 수 없음"을 셀 수 있게 | THINK 1편. 판정 기준이 생김 |
| 2 | 데이터셋 선정 — 공공누리 1유형 확인 + 이중언어 검증 | 후보 3개, 유형 근거, 질문 문장 |
| 3 | 프로젝트 1 + D3 첫 사용 | 별도 배포 + MAKE 1편 |
| 4 | 프로젝트 3 (chart system + 게이트) | 재사용 가능한 것 |
| 5 | 프로젝트 2 (지도) | 별도 배포 + MAKE 1편 |
| 6 | `/practice` 에 `data-visualization` 역량 추가 | 증거 3편이 붙음 |

**Phase 0 이 먼저인 이유는 취향이 아니다.** 발행된 글이 "새 프로젝트 셋을
시작하기 전에 갚는 게 순서다"라고 공개적으로 적었다. 프로젝트를 먼저
시작하면 라이브 상태의 자기 글과 모순된다. 이 사이트의 논지가 "주장은
검증 가능해야 한다"인데 첫 번째로 깨지는 주장이 자기 로드맵이면 안 된다.

**3번과 4번은 리포트와 순서를 뒤집었다.** chart system 을 먼저 만들면
재사용할 것이 없는 상태에서 만들게 된다. 대시보드를 한 번 만들어 봐야
무엇이 재사용 가능한지 안다.

## 자리가 없는 것

`/practice` 는 **주장(이력서) × 증거(사이트)** 두 축이다. "가고 싶은 방향"은
세 번째 축인데 그 페이지에 자리가 없다. 지금은
`think/not-someone-who-draws-charts` 가 그 역할을 하고 있다.

`lib/practice.data.ts` 에 `data-visualization` 역량을 지금 넣을 수는 없다.
`check:practice` 가 "주장도 증거도 없는 역량"을 거부하고, 이력서가 주장하지
않으며 증거도 0 이기 때문이다. **그 거부가 맞다.** 증거가 생기는 Phase 6 에
넣는다.

## 이 문서의 상태

여기 적힌 것 중 **완료된 것은 하나도 없다.** 다른 `docs/` 문서와 달리 이
문서는 검증할 게이트가 없다 — 계획은 게이트로 묶을 수 없기 때문이다.

그래서 이 문서가 낡았는지 판별하는 방법은 하나뿐이다. Phase 가 끝날 때마다
그 줄을 지우고, 무엇이 그것을 끝냈는지 적는다. `docs/BRAND.md` §24 가 열
항목 중 여덟을 그렇게 닫았다. **끝난 항목을 목록에 남겨 두면 로드맵이
거짓말을 시작한다.**
